Baseline versus mesh

The GMCS can route the whole pack but can actively control one drone in mission mode. The other drones carry sensors and a mission computer and use neither: the single-drone GMCS bottleneck. The mesh exploits the drones while they're under pack routing. They scan, share and nominate verifiers on their own. The operator keeps full control of the one drone they fly.

Wide-area scanning

Every drone keeps its direction-finder and imagers running on the route and files each reading with the pack.

Cooperative triangulation

Bearings from several drones intersect by weighted least squares. Near-parallel geometry is rejected.

Mission task prioritisation

Every event gets an urgency from class, novelty, confidence and freshness. All drones compute the same ranking.

Common learning of the situation

One shared table of benign signatures. An operator dismissal reaches every drone, and the drone checking it is released.

Verification and alerting

The best-placed drones approach from different angles. Two sensor types must agree before a PRIORITY alert.

What happens, second by second

10 sPre-briefed weather radio detected; urgency 0.09, ignored.
20.0 sBeacon switches on. Five drones hear it. D1 is 36 km away, out of range.
20.1 sBearings shared and triangulated, CEP 708 m. ADVISORY sent by D4 over LEO SATCOM (it has no LOS). D4 and D6 nominated, from the east and the north. D5, second-nearest, is excluded for fuel.
90 sFault injected: D4 is lost.
94.6 sD6 takes the primary role. With one drone fewer the diversion budget allows one verifier.
100 sNovel ISM emitter appears (urgency 0.45). It waits behind the beacon.
304 sD6 closes to 10 km. IR fixes arrive and the FCS is re-pointed twice as the estimate improves.
328 sTwo sensor types agree: CEP 70 m, actual error 28 m. PRIORITY sent over LOS. D6 released.
420 sOperator dismisses the ISM emitter through D1. Every drone learns it; D2, sent to check it, is released.

The five minutes between the two alerts is flight time. The mesh does not shorten the transit. It starts the right drones at once, from a position estimate good to under a kilometre, and informs the operator meanwhile.

Is the position estimate honest?

A 20,000-trial Monte Carlo at 2.5 degrees of bearing error shows about half of fixes fall inside the reported CEP, as a CEP should (49.9 to 51.5 per cent). Poor geometry has heavy tails: 2 to 6 per cent of fixes are more than three times the CEP off. That is fine for an early warning and is why PRIORITY needs a second sensor type.

How the pack decides

Pack independence: no leader. Every drone folds the same readings into the same table and computes the same plan. Drones with the same table agree without negotiating.

  1. Share. Each drone broadcasts a heartbeat at 1 Hz (position, fuel, active sensor, mode, task) and each sensor reading as it happens. Own readings are re-sent every 2 s so a lost packet only delays convergence.
  2. Fuse. Readings are keyed by observer and sensor and kept in sorted order. Bearings intersect into a position; duplicate events merge into the lowest id.
  3. Rank. evaluateAndCoordinateAlerts() runs every 0.5 s on every drone and ranks events by urgency.
  4. Nominate. For each event the best-fitting free drones are chosen. A drone that finds itself in the plan sends a request to the FCS and claims its slot on the mesh. Claims are arbitrated by quantised score, ties by lowest id, so the holder never depends on arrival order.
  5. Alert. ADVISORY once an event is localised well enough, PRIORITY once two sensor types agree. One drone is the owner, with ranked backups. The GMCS also de-duplicates by event id.

Hard limits and alert levels

eligible:  PACK_ROUTING only
           (ACTIVE_MISSION, RTB never)
fuel:      endurance - bingo
           - (2 x ETA + 300 s) >= 0
corridor:  standoff inside the approved area
budget:    at most floor(0.4 x free drones),
           minimum 1
verifiers: 2 if urgency >= 0.6, else 1

ADVISORY:  severity >= 0.7, confidence >= 0.6,
           CEP <= 2 km
PRIORITY:  confidence >= 0.9, CEP <= 250 m,
           >= 2 observers, >= 2 sensor types

Confidence is a noisy-OR of the readings, capped at 0.85 for one sensor type and 0.99 for two or more. A single sensor type can never confirm an event.

Embedded C++17

Flight-library rules: no exceptions or RTTI, no heap allocation after construction, bounded loops, explicit little-endian wire format. make audit fails the build if the library uses new, throw, std::vector and similar. One PackMeshManager is about 60 KB of fixed storage.

evaluateAndCoordinateAlertssrc/pack_mesh_manager.cpp
void PackMeshManager::evaluateAndCoordinateAlerts(TimeMs now) noexcept {
  last_eval_ms_ = now;
  ++stats_.evaluations;

  // 1. Refresh the shared picture: prune, fuse, merge duplicates, validate slots.
  table_.setSelf(exportedState());
  table_.refresh(now);
  updateUrgencies(table_, now);

  // 2. Every drone with the same table computes the same plan.
  DroneList drones;
  table_.snapshotDrones(drones);
  AssignmentList plan;
  planAssignments(table_, drones, now, cfg_, plan);
  applyAssignments(table_, plan, now);

  // 3. Act on this drone's part of the plan.
  const Assignment* mine = nullptr;
  for (const auto& a : plan) {
    if (a.drone == self_) mine = &a;
  }
  syncOwnTask(mine, now);

  // 4. Early-warning and verified alerts to the GMCS (one owner per event).
  dispatchAlerts(now);
}

Not done yet

Read these before relying on any of this.

  • No authentication or encryption.Packets carry a CRC, which catches accidents but not an attacker. A real mesh needs authenticated encryption, key management and replay protection.
  • No flight validation.Every performance figure comes from a simulation with idealised sensors, zero radio latency and a range limited only by distance.
  • The 8270's real interfaces are assumed.All hardware access goes through one abstraction layer. The buses in the diagram are recommendations.
  • The FCS interface has no reply.A real one needs accept and refuse.
  • Time assumes a shared GNSS-disciplined clock.GNSS-denied operation is not handled.
  • The corridor is a circle.A real approved corridor is a polygon.
  • Forged packets.Packets naming another drone as sender, future timestamps and absurd values are rejected, but a forged frequency dismissal or alert notice still works without authentication.
  • Mesh partitions are untested.Each side of a split keeps working by design and the GMCS de-duplicates alerts, but no test covers it.
The system detects, localises, verifies and alerts. It has no weapons or engagement logic and does not command flight controls: it sends requests to the FCS. Repository: drones-mesh/ with docs, include/, src/, tests/ and sim/.
